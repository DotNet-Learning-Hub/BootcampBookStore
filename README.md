# فروشگاه کتاب — راهنمای ساده‌ی مطالعه و Code Review

این پروژه یک فروشگاه کتاب ساده و کنسولی است که با **C#** و **.NET 8** نوشته شده است. هدف پروژه، تمرین مفاهیم پایه‌ی برنامه‌نویسی شی‌گرا، تفکیک مسئولیت‌ها، مدیریت نقش‌ها و بررسی کد (Code Review) است.

> داده‌ها فقط داخل حافظه نگهداری می‌شوند؛ بنابراین با بستن برنامه، تمام تغییرات از بین می‌روند و اطلاعات اولیه دوباره ساخته می‌شوند.

## پروژه چه کارهایی انجام می‌دهد؟

کاربر می‌تواند وارد برنامه شود و متناسب با نقش خود کارهای مختلفی انجام دهد:

- مشاهده‌ی فهرست کتاب‌ها و پروفایل
- تغییر رمز عبور
- ثبت کتاب و تغییر قیمت توسط مدیر
- ساخت سفارش و افزودن کتاب توسط مشتری
- مشاهده‌ی سفارش‌های مجاز
- نهایی کردن سفارش و کم کردن موجودی توسط مدیر یا اپراتور
- تغییر آدرس توسط مشتری

## پیش‌نیاز و اجرای پروژه

ابتدا مطمئن شوید **.NET 8 SDK** نصب است:

```bash
dotnet --version
```

سپس در پوشه‌ی پروژه این دستور را اجرا کنید:

```bash
dotnet run
```

برای اطمینان از کامپایل شدن پروژه نیز می‌توانید بنویسید:

```bash
dotnet build
```

## ساختار پروژه

```text
Mentor-Solution/
├── Program.cs                  ورودی برنامه، منوها و دریافت اطلاعات از کاربر
├── Data/
│   └── ShopStorage.cs          نگهداری داده‌های موقت و اطلاعات نمونه
├── Domain/
│   ├── Entities/               موجودیت‌های اصلی: User، Book، Address و EBook
│   ├── Enums/                  نقش‌ها، مجوزها و وضعیت‌ها
│   ├── PrintedBook.cs          کتاب چاپی و منطق موجودی و ارسال
│   ├── Order.cs                سفارش و قوانین مربوط به آیتم‌های آن
│   └── OrderItem.cs            یک ردیف از سفارش و محاسبه‌ی مبلغ آن
├── Services/
│   ├── AccessService.cs        کنترل سطح دسترسی
│   ├── UserService.cs          ورود، رمز عبور، آدرس و کاربران
│   ├── BookService.cs          کاتالوگ، ثبت کتاب و تغییر قیمت
│   └── OrderService.cs         ساخت، مشاهده و نهایی کردن سفارش
└── Helpers/
    └── ConsoleKit.cs           رنگ و ظاهر خروجی کنسول
```

## معماری پروژه به زبان ساده

برنامه چهار بخش اصلی دارد:

1. **Presentation (`Program.cs`)**: با کاربر صحبت می‌کند؛ ورودی می‌گیرد و نتیجه را نمایش می‌دهد.
2. **Services**: قوانین و سناریوهای برنامه را اجرا می‌کند؛ برای مثال بررسی می‌کند چه کسی اجازه‌ی تغییر قیمت دارد.
3. **Domain**: مدل‌های اصلی کسب‌وکار و رفتار آن‌ها را نگه می‌دارد؛ مانند کتاب، کاربر و سفارش.
4. **Data (`ShopStorage`)**: داده‌ها را به‌صورت آرایه‌های ثابت و موقت در حافظه نگه می‌دارد.

مسیر معمول یک درخواست به این شکل است:

```text
کاربر ← Program.cs ← Service ← Domain / ShopStorage
```

برای مثال هنگام تغییر قیمت:

1. `Program.cs` شناسه‌ی کتاب و قیمت جدید را می‌گیرد.
2. `BookService` مجوز کاربر و معتبر بودن قیمت را بررسی می‌کند.
3. `ShopStorage` کتاب را پیدا می‌کند.
4. متد `Book.ChangePrice` قیمت را تغییر می‌دهد.
5. یک `OperationStatus` برای نمایش نتیجه برگردانده می‌شود.

## مدل‌های مهم پروژه

### کتاب‌ها

`Book` یک کلاس abstract و پایه‌ی همه‌ی کتاب‌ها است. دو نوع کتاب داریم:

- `PrintedBook`: موجودی و هزینه‌ی ارسال دارد.
- `EBook`: فرمت فایل دارد و هزینه‌ی ارسال آن صفر است.

این قسمت نمونه‌ای ساده از **ارث‌بری** و **Polymorphism** است. هر نوع کتاب، محاسبه‌ی هزینه‌ی ارسال و توضیح خودش را پیاده‌سازی می‌کند.

### سفارش

هر `Order` متعلق به یک مشتری است و حداکثر ۱۰ ردیف دارد. سفارش ابتدا در وضعیت `Draft` ساخته می‌شود و پس از Checkout به وضعیت `Placed` می‌رود.

هنگام اضافه شدن یک کتاب، قیمت و هزینه‌ی ارسال در `OrderItem` ثبت می‌شوند. به همین دلیل تغییر بعدی قیمت کتاب، مبلغ سفارش قبلی را عوض نمی‌کند.

### نقش و مجوز

`UserRole` نقش کاربر را مشخص می‌کند، اما تصمیم نهایی درباره‌ی هر دسترسی در `AccessService` گرفته می‌شود. سرویس‌های دیگر نیز مجوز را دوباره بررسی می‌کنند؛ پس مخفی بودن گزینه‌ای در منو، تنها محافظ برنامه نیست.

### وضعیت عملیات

متدهای تغییردهنده معمولاً به‌جای `true` و `false` یک مقدار از `OperationStatus` برمی‌گردانند؛ مانند:

- `Success`
- `AccessDenied`
- `BookNotFound`
- `OutOfStock`
- `WeakPassword`

این روش به رابط کاربری اجازه می‌دهد علت دقیق شکست عملیات را نمایش دهد.

## سناریوی پیشنهادی برای تست دستی

1. با کاربر `sara` وارد شوید.
2. کاتالوگ را ببینید و یک سفارش بسازید.
3. یک کتاب چاپی و یک کتاب الکترونیکی به سفارش اضافه کنید.
4. جزئیات سفارش و مبلغ کل را بررسی کنید.
5. خارج شوید و با `operator` وارد شوید.
6. سفارش را مشاهده و Checkout کنید.
7. دوباره کاتالوگ را باز کنید؛ موجودی کتاب چاپی باید کم شده باشد.
8. تلاش کنید همان سفارش را دوباره Checkout کنید؛ باید `AlreadyPlaced` دریافت شود.

چند حالت خطا را هم امتحان کنید: تعداد صفر، شناسه‌ی نامعتبر، افزودن دوباره‌ی یک کتاب، سفارش خالی و موجودی ناکافی.

## مسیر پیشنهادی مطالعه‌ی کد

برای اینکه کد گیج‌کننده نباشد، فایل‌ها را با این ترتیب بخوانید:

1. `Domain/Enums` برای شناخت نقش‌ها و وضعیت‌ها
2. `Domain/Entities` و سپس `PrintedBook`، `OrderItem` و `Order`
3. `Data/ShopStorage.cs` برای شناخت داده‌های اولیه
4. `Services/AccessService.cs` برای قوانین دسترسی
5. سه سرویس `UserService`، `BookService` و `OrderService`
6. در پایان `Program.cs` برای دیدن اتصال همه‌ی بخش‌ها

هنگام مطالعه، یک سناریو مثل «افزودن کتاب به سفارش» را انتخاب کنید و حرکت داده را از `Program.cs` تا سرویس، حافظه و مدل دنبال کنید.

## راهنمای خیلی ساده‌ی Code Review

Code Review یعنی بررسی کنیم کد **درست، خوانا، امن و قابل تغییر** هست یا نه. هدف پیدا کردن مقصر نیست؛ هدف بهتر شدن کد و یادگیری تیم است.

### گام اول: رفتار را بفهمید

- پروژه را اجرا کنید.
- یک سناریوی موفق و چند سناریوی ناموفق را آزمایش کنید.
- مشخص کنید هر نقش باید به چه امکاناتی دسترسی داشته باشد.

### گام دوم: مسئولیت فایل‌ها را بررسی کنید

- آیا `Program.cs` فقط ورودی و خروجی را مدیریت می‌کند؟
- آیا قوانین کسب‌وکار داخل Domain یا Service هستند؟
- آیا کنترل دسترسی فقط به نمایش منو وابسته نیست؟
- آیا هر کلاس یک مسئولیت روشن دارد؟

### گام سوم: ورودی‌ها و حالت‌های مرزی را پیدا کنید

برای هر متد از خودتان بپرسید:

- اگر ورودی `null`، خالی، صفر یا منفی باشد چه می‌شود؟
- اگر کتاب، کاربر یا سفارش وجود نداشته باشد چه می‌شود؟
- اگر ظرفیت آرایه پر شود چه می‌شود؟
- اگر سفارش قبلاً نهایی شده باشد چه می‌شود؟
- آیا شکست در میانه‌ی عملیات، داده‌ها را نیمه‌کاره تغییر می‌دهد؟

### گام چهارم: خوانایی را بررسی کنید

- آیا نام کلاس، متد و متغیر هدف آن را روشن می‌کند؟
- آیا متد بیش از حد طولانی یا تودرتو است؟
- آیا کد تکراری وجود دارد؟
- آیا کامنت دلیل تصمیم را توضیح می‌دهد، نه چیزی که خود کد می‌گوید؟

### گام پنجم: امنیت و طراحی واقعی را در نظر بگیرید

این پروژه عمداً ساده و آموزشی است. در یک برنامه‌ی واقعی باید این موارد بررسی شوند:

- رمز عبور نباید به‌صورت متن ساده ذخیره شود؛ باید Hash و Salt شود.
- داده‌ها باید در دیتابیس پایدار ذخیره شوند.
- ظرفیت داده‌ها نباید به آرایه‌های ثابت محدود باشد.
- Checkout هم‌زمان باید تراکنش و کنترل هم‌روندی داشته باشد.
- ورودی و خطاها باید ثبت و مدیریت شوند.
- برای قوانین مهم باید تست خودکار نوشته شود.

## چطور یک نظر خوب در Code Review بنویسیم؟

نظر خوب، دقیق و محترمانه است و دلیل و پیشنهاد دارد.

نمونه‌ی نامناسب:

> این کد بد است.

نمونه‌ی بهتر:

> در این متد قیمت منفی پذیرفته می‌شود و ممکن است مبلغ سفارش اشتباه شود. بهتر است قبل از تغییر قیمت، مقدار `newPrice` اعتبارسنجی شود.

قالب ساده‌ی پیشنهادی:

```text
موضوع: مشکل چیست؟
اثر: چه خطا یا هزینه‌ای ایجاد می‌کند؟
پیشنهاد: چطور می‌توان آن را بهتر کرد؟
```

شدت نظر را نیز مشخص کنید:

- **ضروری (Blocker):** خطای جدی، مشکل امنیتی یا رفتار نادرست
- **پیشنهاد (Suggestion):** بهبود طراحی، خوانایی یا نگهداری
- **سؤال (Question):** بخشی که هدف یا دلیل آن روشن نیست
- **نکته‌ی کوچک (Nit):** تغییر جزئی و سلیقه‌ای

## تمرین‌های پیشنهادی برای هنرجو

- برای `UserService.IsStrongPassword` تست بنویسید.
- ثبت `EBook` را به منوی مدیر اضافه کنید.
- امکان حذف یک ردیف از سفارش Draft را پیاده‌سازی کنید.
- پیام خطاهای `OperationStatus` را فارسی و کاربرپسند کنید.
- آرایه‌های ثابت `ShopStorage` را با Collection مناسب جایگزین کنید.
- وابستگی مستقیم سرویس‌ها به `ShopStorage` را با Repository یا Interface کمتر کنید.
- بررسی کنید ساخت Order ID در صورت پر بودن حافظه چه رفتاری دارد.
- برای Checkout تست‌های سفارش خالی، موجودی ناکافی و اجرای دوباره بنویسید.

## محدودیت‌های آگاهانه‌ی پروژه

این نسخه برای کلاس و یادگیری ساخته شده است، نه محیط Production:

- دیتابیس، API و رابط گرافیکی ندارد.
- داده‌ها بعد از خروج پاک می‌شوند.
- تعداد کتاب، کاربر، سفارش و ردیف‌های سفارش محدود است.
- رمزها متن ساده‌اند.
- تست خودکار و سیستم Log وجود ندارد.
- برنامه تک‌نخی فرض شده و برای درخواست‌های هم‌زمان مناسب نیست.

همین محدودیت‌ها می‌توانند نقطه‌ی شروع خوبی برای تمرین Refactoring و Code Review باشند.
